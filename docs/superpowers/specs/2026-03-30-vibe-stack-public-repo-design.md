# Vibe Stack Public Repo Restructure

**Date:** 2026-03-30
**Status:** Approved
**Goal:** Make Vibe Stack a fully open-source, self-hostable multi-agent platform that anyone can clone and run on their own hardware.

## Target Experience

```bash
git clone https://github.com/tmartin2113/Vibe-Stack.git
cd Vibe-Stack
./setup.sh
docker compose up -d
```

Three commands (plus setup interaction) to a working multi-agent system.

## Repository Structure


### Key Changes From Current State

- All service definitions tracked in git. The gitignored `docker-compose.override.yml` no longer contains critical infrastructure — it becomes truly optional for personal dev mounts and debug ports.
- Three composable compose files replace the monolithic override.
- Hardcoded agent replicas (vibe-eng-1/2/3) removed from compose. Agent provisioning is handled through the Paperclip UI.

## Docker Images & Build Strategy

### Pre-Built Images (GHCR, from paperclip fork CI)

| Image | Source | Tag Strategy |
|-------|--------|-------------|
| `ghcr.io/tmartin2113/paperclip-server` | `paperclip/Dockerfile` | `latest` + semver |
| `ghcr.io/tmartin2113/deerflow-langgraph` | `paperclip/deerflow/backend/Dockerfile` | `latest` + semver |
| `ghcr.io/tmartin2113/deerflow-gateway` | `paperclip/deerflow/backend/Dockerfile` (different CMD) | `latest` + semver |

### Locally Built (from Vibe Stack clone)

| Image | Source |
|-------|--------|
| `vibe-stack-vibe` | `./Dockerfile` |
| `vibe-stack-ssh-relay` | `./ssh-relay/Dockerfile` |
| `vibe-stack-dev-runner` | `./dev-runner/Dockerfile` |

### Version Pinning

`docker-compose.yml` references images with a `PAPERCLIP_VERSION` variable defaulting to `latest`. `setup.sh` can pin to a tested version. Users can override to any tag.

### Dev Override for Local Hacking

Developers who want to modify the paperclip server or DeerFlow can add a `docker-compose.override.yml` (gitignored) with local build contexts:

```yaml
services:
  server:
    build:
      context: /path/to/paperclip
    volumes:
      - /path/to/paperclip/server/dist:/app/server/dist
```

Default path pulls pre-built images. Local build is opt-in.

### CI Pipeline (paperclip fork)

- Trigger: push to release branch
- Steps: build all three images, push to GHCR with `latest` + semver tags
- DeerFlow langgraph and gateway use the same Docker image; compose overrides the `command:` to select langgraph server vs gateway uvicorn

### COMPOSE_FILE Auto-Configuration

`setup.sh` writes a `COMPOSE_FILE` variable to `.env` based on detected hardware. Docker Compose natively reads this, so `docker compose up -d` always does the right thing.

| Hardware | COMPOSE_FILE | Services |
|----------|-------------|----------|
| GPU + full stack | `docker-compose.yml:docker-compose.infra.yml:docker-compose.gpu.yml` | 18 |
| No GPU | `docker-compose.yml:docker-compose.infra.yml` | 15 |
| Minimal | `docker-compose.yml` | 5 |

### Networking

- `default` network for inter-service communication
- `agent-network` bridged network for vibe agent replicas to reach services
- Services needing host access get `extra_hosts: host.docker.internal:host-gateway`

## Setup Flow

### Phase 1 — Prerequisites Check

Checks for Docker, Docker Compose, Git, Tailscale. Fails fast with exact one-line fix instructions for each missing prerequisite.

### Phase 2 — Hardware Detection

Detects GPU model and VRAM, RAM, disk space. Recommends vLLM model tier:

| VRAM | Model |
|------|-------|
| 48GB+ | Qwen/Qwen3.5-27B |
| 24GB | Qwen/Qwen3.5-27B-GPTQ-Int4 |
| 12GB | Qwen/Qwen3.5-9B |
| 8GB | Qwen/Qwen3.5-4B |
| None | GPU tier disabled, cloud-only mode |

Shows recommendations, asks for confirmation.

### Phase 3 — Secrets Generation

Auto-generates all secrets: Agent JWT, auth secret, Postgres password, SearXNG secret, MinIO credentials. Writes to `secrets/` directory. Idempotent — re-running does not overwrite existing secrets.

### Phase 4 — Skill Sources (Optional)

Asks whether to fetch community skill sources. Fetches with pinned commits/tags for reproducibility:
- anthropics-skills
- openclaw-skills
- vercel-agent-skills
- obra-superpowers
- voltagent-skills

### Phase 5 — Network Setup

Detects Tailscale hostname and IP. Configures HTTPS access URL.

### Phase 6 — Write Config & Pull

Writes `.env` with all configuration including `COMPOSE_FILE`. Pulls all Docker images. Prints the access URL and startup command.

### Design Principles

- Every failure has a one-line fix instruction
- No question requires domain knowledge — defaults are always safe
- Idempotent — run again after upgrades, only changes what's needed
- Modular functions internally — ready to evolve into a TUI/CLI

## Tiered Agent Execution

### The Model

Cloud adapter agents (Claude, GPT, Codex) handle high-level reasoning, spec-building, and complex decisions. DeerFlow handles menial work — file operations, search, tool use, code execution — using the local vLLM model. Users don't configure this; it's automatic.

### Auto-Provisioning

When a user creates a cloud adapter agent in Paperclip:

1. Server detects whether vLLM is available (health check on DeerFlow-gateway)
2. If available: auto-creates a paired DeerFlow assistant agent, links it to the cloud agent
3. Cloud agent delegates tool-heavy subtasks to its DeerFlow assistant transparently
4. If vLLM unavailable: no assistant created, cloud agent works solo

### Graceful Degradation

| vLLM Status | Cloud Adapter Behavior | Local Adapter Behavior |
|-------------|----------------------|----------------------|
| Running | Cloud handles reasoning. DeerFlow handles tool execution via vLLM. | Full local pipeline. |
| Not running | Cloud handles everything. DeerFlow idle. | Adapter reports unavailable. |

- DeerFlow services always start (defined in core compose)
- DeerFlow-langgraph returns degraded status when vLLM is unreachable
- No crash, no retry loop — graceful fallback
- Paperclip dashboard shows capability tier: "Cloud + Local" vs "Cloud Only"

### Paperclip Server Changes Required

- Agent creation endpoint: detect cloud adapter + vLLM healthy → auto-create paired DeerFlow agent
- Agent model: add `assistant_agent_id` field linking cloud agent to DeerFlow assistant
- Task routing: cloud adapter checks for linked assistant, delegates tool-heavy subtasks

## Agent Replicas

No hardcoded replicas in compose files. Agent provisioning is entirely through the Paperclip UI:

1. User runs `./setup.sh` → starts services → opens Paperclip at the Tailscale URL
2. Creates org, creates agents with cloud adapters
3. DeerFlow assistants auto-provisioned for each cloud agent (when GPU available)

Future CLI/TUI can add `vibe agents add` that talks to the Paperclip API directly.
